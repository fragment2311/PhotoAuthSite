# Состав устройств точки: целевая модель

## Статус

Согласованный проект изменений. Миграция и изменения кода этим документом не выполняются.

## Цель

Убрать жёсткую модель «контроллер + входная камера + выходная камера» и хранить состав точки как список устройств. Модель должна позволять добавить вторую камеру через сайт без нового изменения схемы.

## Границы

- Текущий проект сервера: `PhotoAuthApp — копия`.
- Клиенты: SkudConsole и SmartPass.
- Редактирование состава точки выполняет администратор на сайте.
- Бизнес-логика проходов не меняется.

## Решения

1. Использовать существующую таблицу `PairDeviceDevices`, не создавать новую.
2. Одна строка `PairDeviceDevices` описывает одно устройство в одной точке.
3. Устройство может принадлежать только одной точке.
4. Поддерживаемые роли: `controller`, `entry_camera`, `exit_camera`.
5. Роль уникальна в пределах точки; двух камер одной роли в первой версии нет.
6. Точку можно сохранить с контроллером и любой одной камерой. Камера входа не является обязательной для сохранения.
7. Старые строки связи считаются нерабочими данными: таблица с ними и прежнее поле связи сохраняются с суффиксом `Legacy`.

## Целевая структура

```text
PairDeviceDevices
- Id
- IdPairDevice       -> pairdevices.Id
- IdController       -> controllers.Id, nullable
- IdCamera           -> cameras.Id, nullable
- Role               controller | entry_camera | exit_camera
- SortOrder
- IsActive
```

В каждой строке заполнен ровно один идентификатор устройства: `IdController` или `IdCamera`. Для роли `controller` заполняется `IdController`; для ролей камер — `IdCamera`.

Ограничения БД:

- внешний ключ `IdPairDevice`;
- внешний ключи к контроллерам и камерам;
- уникальные `IdController` и `IdCamera`, чтобы исключить привязку устройства к двум точкам;
- уникальная пара `IdPairDevice + Role`, чтобы не повторять роль в точке.

## Сайт и API

Форма точки показывает список устройств. Администратор выбирает роль и устройство, добавляет или удаляет строки. Устройства, уже привязанные к иной точке, не предлагаются для выбора.

Основным ответом является `GET /api/device-pairs/active?format=v2` с массивом `devices[]`. Для миграционного периода сервер дополнительно собирает поля `controller`, `entry_camera`, `exit_camera` из массива.

Если у точки нет камеры роли, требуемой конкретным сценарием прохода, клиент сообщает контролируемую ошибку во время этого сценария; сервер не блокирует сохранение точки только из-за отсутствия камеры входа.

## Клиенты

- SkudConsole получает `devices[]`, выбирает контроллер и камеры по `role` и использует `factory_code` для каталога фото.
- SmartPass получает тот же массив и выбирает необходимые устройства по `role`.
- Оба клиента продолжают передавать `X-Api-Token`, `X-Client-Id`, `X-Request-Id`, `Accept: application/json`.

## Порядок выполнения и проверка

1. Сделать резервную копию `pairdevices` и `pair_device_devices`.
2. Сохранить прежнюю таблицу с суффиксом `Legacy`, создать новую связь и ограничения.
3. Обновить серверную модель, сайт, v2 API и совместимый v1 API.
4. Обновить SkudConsole и SmartPass, затем пересобрать их.
5. Проверить создание точки с контроллером и одной камерой, добавление второй камеры, API v2 и загрузку тестового фото.

Предположения: объём данных небольшой, редактирование выполняют только администраторы, миграция выполняется в окно обслуживания, технические трассировки хранятся в файловом логе, а не в таблице `Logs`.
